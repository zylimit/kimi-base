# 沟通桥梁层评审与重构设计（v3.0 软层）

日期：2026-09-08 · 依据：软层审计（16 skills/8 agents/13 模板/8 命令逐行，行号取证）+ 外部调研（12 次检索、ReqElicitGym / Knowing-but-not-showing / Lost-in-Conversation / QuestBench / ClarifyGPT / Fowler SDD 框架等）+ 对照组 cc-base/dsh-base。

## 1. 对问题的具体理解

kimi-base 的工程面会机械地证明"代码做对了"，但**没有任何机制保证"做对的是用户真正要的东西"**。框架的另一半——人和 AI 共同理解问题、形成判断、完成交付的沟通桥梁——在三个根源上断裂：

1. **认知无标注**：用户确认的事实、AI 的推断、建议、未知项在所有产物里不可区分。唯一例外是 progress-recorder 的置信度闸门和 researcher 的三档标注，但都止步于记忆层，进不了 Spec。
2. **业务含义不过链**：REQ 只传"做什么"不传"为什么"；派单六字段没有业务上下文；到 implementer 时业务语境归零，code-review 只能核字面符合。
3. **交互深度一刀切**：签字闸是唯一确认机制；审批三档按操作风险分，没有按"认知不确定性 × 做错代价"分的交互档；没有"问过的不再问"。

外部实证给了这三个断点硬证据：模型被问时能判断歧义、但默认 >95% 直接作答（knowing-but-not-showing，RLHF 奖励"显得有用"）；多轮修补欠规约需求平均性能掉 39%（Lost-in-Conversation）；LLM 平均只引出不到一半隐性需求（ReqElicitGym）；识别"该问什么"是独立能力且很弱（QuestBench 40-50%）。**结论：认知标注不能靠模型自觉，必须做成模板强制字段与引擎检查；访谈要"冻结成文、干净执行"；隐性知识要靠结构化清单挖而非指望自发。**

## 2. 偏差证据（审计取证）

### 系统性断点（每个都有行号证据，详见审计底稿）

- **断点 1｜Spec 不带"为什么"，业务含义逐级蒸发**：Product-Spec 模板 REQ 格式无动机/受益人/来源字段；implementer 派单包六字段无业务上下文（agents/implementer.md:20-28）；code-review Stage 1 对照 REQ 只能核字面（code-review/SKILL.md:39）。
- **断点 2｜无下游→上游反例回流**：bug-fixer 要求"问到流程/契约层才停"（bug-fixer/SKILL.md:31）但根因结论只进回执不回写 Spec；code-review 发现 Spec 矛盾无上报通道；cc-base 有明确的"需求存疑回流 psb 迭代模式"机制，kimi 全链没有。
- **断点 3｜认知无标注贯穿全链**：psb 充足度门要求"每维写成可判定条目"（psb L55）在无法标注推断时**激励 AI 把猜测写成事实**——"诚实充足度"与"缺一维即废纸"互相打架，后者赢。dev-planner 无法做"关键未知排序"，因为没有 [推断] 清单可排。
- **断点 4｜迭代模式不采集"为什么改、原来哪条判断错了"**（psb L77-84 只做变更分级+冲突检测），同类需求错误反复发生。
- **断点 5｜界面/UX 阶段整体缺失**：无真实任务分析、无操作环境/认知习惯采集、无可体验原型要求。
- **断点 6｜签字闸一刀切**：psb L80 说轻度"确认理解正确即可"、L84 又要求"必须用户明确批准"——自相矛盾，实践中必然演化成仪式性点头；无直推档/委托档/澄清记录。
- **断点 7｜记忆只存"是什么"不存"为什么、适用于哪、被谁修正"**：progress 模板决策"理由：可选"；无 supersede 链；evolution 规则毕业后与来源 feedback 脱钩。

### 工艺缺口

全部 16 个 skill **无一个多轮对话示例**；反例仅散见禁写清单；无"怎么理解答案"解析器（听到"都要"→逼取舍、听到弱化词→标推断要例子）；无"答案怎样改变下一步"路由表；交接只有"引导下一 skill"一句话。对照 cc-base product-spec-builder（138 行几乎行行是机制）在这些维度上完整。

### 重复/无效（消除面）

回执六字段模板逐字重复 20+ 处；8 个 agent 末尾"交接声明"逐字重复；意图路由表双份（sessionStart + AGENTS.md 模板）必然漂移；"联网优先"5+ 处重复；六维"缺一即废纸"的填表激励；arch 七原则逐条填表对中小项目退化为仪式。

## 3. 改进取舍

**保留（骨架是对的）**：REQ 锚定链与只增不复用、派单/回执六字段协议、签字闸本身（补豁免档不拆闸）、对抗审查姿态、证据法、S/M/L 分级雏形、progress-recorder 置信度闸门、feedback→evolution 闭环、"fast 是借账不是折扣"。

**不跟的流行做法（有实证依据的拒绝）**：小改动套全套 SDD 流水线（review overload）、BMAD 式角色剧场（无对照证据）、branch-per-spec 厚生成物（工件越厚人越不读）、事后补 Gherkin、无阈值"多问澄清"、spec-as-source。

**核心改进（按杠杆排序）**：

1. **认知标注进 Spec（三态强制字段）**：`[确认]`（用户确认的事实+来源）/`[推断]`（AI 推断+依据）/`[待定]`（未知+需要谁回答）；未标按推断论处。spec lint 引擎检查：active REQ 块存在未标态条款 → warning→error 可调。这是断点 3 的根治，后续"关键未知排序""交接质量"都建立在它上面。
2. **业务含义过链**：Spec REQ 增"动机/受益人/来源"字段；派单包加第七字段"业务上下文"（主 Agent 从 Spec 抄，不许 fresh 实例猜）；code-review/bug-fixer/test-builder 增"需求存疑"回流通道（回流 psb 迭代模式，反例进 Spec 的"规则与例外"节）。
3. **交互深度四档**：直推（清楚小任务）/确认（默认）/探索（重要且不清楚）/委托（用户说"你定"→自己定+记入决策依据+不再回头问）；判据=认知不确定性×做错代价；"问过的不再问"（澄清记录持久化，重问须先摆出矛盾新事实）；签字闸对直推档豁免——解决 L80/L84 矛盾。
4. **psb 方法层重写**：向人学业务四线（as-is 真实故事/受益受损者/规则与例外/决策历史）、问"上一次"不问"一般来说"（CTA 关键决策法）、答案解析器、答案→下一步路由表、情境复述收敛（用用户的案例讲"那次会怎么走"，不问"对吗"）、收敛条件=待定清零+复述通过（维度清单降级为覆盖检查器）。
5. **记忆依据链**：Decisions 强制三字段（理由+被否方案+适用范围）；supersede 显式链；evolution 毕业保留来源 feedback 指针；纠正后产出"旧理解→新理解→影响面"三段式（diff-of-understanding），不止于道歉或一条 feedback。
6. **阶段专业化**：arch 补业务推导线（数据归属/一致性/故障后果/团队能力→取舍解释）；dfx 补定标方法（业务损失与可接受边界→目标值）；界面阶段补"真实任务走查"最低要求。
7. **工艺补齐**：每个对话型 skill 补 2-3 个多轮对话示例+反例清单；执行型 skill 补"反合理化清单"（偷懒话术→应对）；去重下沉（回执信封/交接声明/路由表/联网优先各留一处定义）。

## 4. 与工程面的接口

软层机制同样服从"可执行检查优先"公理：认知标注由 spec lint 机械检查；澄清记录/纠正三段式有文档模板+progress 格式；交互四档由 workflow.md 承载、strength 引擎的 completionMode 联动（委托档=用户显式授权判断）；访谈产物冻结成文后进开发（Lost-in-Conversation 对策：spec 是唯一真相源，对话补丁禁止）。

## 5. 验证方法（可观察的前后行为）

每个改进点配"真实情境检验"：用同一业务场景（虚构但具体的客户故事）分别走改进前/后的 skill，对比：隐性需求召回数、推断冒充事实的次数、返工轮次、用户需要重复表达的次数。该检验套件进 tests/ 或 docs 案例库（P11 收尾验收）。
