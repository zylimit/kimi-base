# Dev Planner — 开发计划

## 任务

**生成模式**：读取已批准的 `Product-Spec.md`，分析功能依赖关系，WebSearch 验证技术选型，产出分阶段开发计划 `DEV-PLAN.md`。

**迭代模式**：Spec 变更后分析影响范围，更新 Phase 划分与文件清单；已完成（标 ✅）的 Phase 不动。

## 依赖检测

- 必需：`Product-Spec.md`（且已经用户签字批准）→ 缺失则提示先走 product-spec-builder
- 可选：`Architecture-Design.md` / `DFX-Spec.md`（有则 Phase 按模块边界拆、DFX 验证手段进 Phase 验收）；已有代码（有则扫描现有结构作约束，进入迭代模式）

## 第一性原则

**可验证**：每个 Phase 完成后必须能编译、能运行、能看到效果。不允许"写一堆代码但什么都跑不起来"的 Phase。

**依赖正序**：地基先打。基础设施（骨架、数据库、路由）永远排在业务功能前；被依赖方先做。

**粒度适中**：一个 Phase 对应一个可独立验收的功能单元，含 **2-5 个 Task**。数值信号（命中任一即行动）：

- **太大须拆**：交付物 >5 项；或关键文件 >10 个；或一个 Phase 装 >3 个互不相关的功能（判据：其中任何一个砍掉，其余照常验收 = 不相关）。
- **太碎须并**：只有 1 个交付物且只动 1-2 个文件——与相邻 Phase 合并，不为一行改动单独立项。

**无占位符**：Plan 里每个字都要具体到一个没有项目上下文的工程师也能直接开工：

- 不允许：TBD、TODO、"待补充"、"待确定"
- 不允许："类似 Task N"——重复具体内容，不引用
- 不允许："添加适当的错误处理"——指明处理什么错误、怎么处理
- 不允许："实现相关功能"——列出具体功能名称和行为
- 不允许："写测试"——写清覆盖什么、跑什么命令、期望什么结果

**按最坏执行者设防**：Task 的执行者是对项目零上下文的 fresh 子代理，且可能按最字面、最省力的方式理解指令。每个 Task 必须自足：目标、边界、验证全写死，不给"自由发挥"留缝。

**联网优先**（规则单源：`.kimi-base/rules/workflow.md`「联网优先」节）：本 skill 的触发场景 = 技术栈选型与关键依赖版本。

## Task 五要素（每个 Task 必须写齐）

```text
Goal:         明确实现什么行为（一个可独立验收的切片）
Scope:        精确到文件路径的改动范围（新建/修改哪些文件）
Dependencies: 前置依赖（无 / 必须在 Task X.Y 之后，因为……）
Verification: 具体验证命令（可逐字执行）
Expected:     可判定的预期结果（退出码 0 / 输出含某关键文本 / 某行为可观察）
```

五要素缺一，该 Task 不得进 Plan。

## 分析策略

**DAG 拓扑排序**：列出全部功能点 → 逐功能问「它能独立运行吗？依赖谁？」→ 建有向无环图 → 拓扑排序得 Phase 顺序。基础设施是 DAG 根节点。发现环 → 停下解环，不许带着环排期。

**洋葱剥皮（由内到外）**：无强依赖时按用户感知价值排序——核心功能（砍掉产品不成立）→ 重要功能 → 辅助功能 → 收尾（打包、部署）。

**风险前置**：技术风险最高的部分（新技术、复杂集成、不确定 API）排到早期 Phase：没用过的框架在骨架 Phase 就验证；关键第三方 API 早期做集成验证；性能敏感功能实现时就考虑，不留到最后。切片内部同样成立——**不确定性最高的切片最先做**，先让最大未知数现形，再排确定的活；把高风险切片排到最后 = 把进度谎言养到截止日前一天。

**REQ 覆盖核对**：Spec 中每条 REQ 必须落到某个 Phase 的交付清单；Plan 末尾列 REQ → Phase 映射表，漏一条就是漏需求。

**「不需要分析」显式排除清单**：以下变更不进计划阶段，直接做或走轻量通道，不套 Phase/Task 流水线——

- 纯文案/注释/文档表述修改，不改行为；
- 单文件内的重命名、格式化、死代码删除（不产生新违规边）；
- 依赖补丁级升级（无 API 变更，测试全绿即可）；
- 已在既有 Phase 交付清单内、只是被顺延的 Task。

边界判据：改动是否新增/改变可观察行为或跨模块契约？是 → 过计划；否 → 排除清单内直接做。拿不准按「过计划」处理，但只产最小计划（一个 Phase 一个 Task），不硬凑 2-5 个。

**确认策略**：dev-planner 不需要大量对话，只在以下情况问用户——技术栈有多个合理选项（给 2-3 方案 + 优劣）；Phase 粒度偏好；功能优先级有歧义。其余按 Spec 执行。

## 信息充足度判断

**必须满足**：技术栈已定（经 WebSearch 验证）；Phase 拆分完成且依赖顺序无环；每个 Phase 过粒度数值信号（未命中「太大/太碎」或已按信号拆并）且风险最高的切片排在最前；每个 Phase 有交付清单 + 关键文件（具体路径）+ 2-5 个五要素齐全的 Task；Spec 全部 REQ 有归属。

**尽量满足**：数据库表梳理（表名 + 所属 Phase + 用途）；每 Phase 验收标准（最低：能编译、能启动、新功能可用；推荐加：现有功能未破坏）；已知风险标注。

必须满足未达成 → 继续分析，不产出半成品。

## 工作流程（生成模式）

1. **加载**：读 Product-Spec.md（含五性需求与非目标）；有 Architecture-Design.md / DFX-Spec.md 则读（Phase 按模块边界拆，DFX 验证手段进对应 Phase 验收）；有 `[待补充]` 标记 → 列出并请用户先补或确认跳过；已有代码则扫描结构作约束。
2. **技术验证**：提取/推荐技术栈 → WebSearch 验证版本与兼容性 → 输出技术栈表（框架 + 版本 + 关键依赖）。
3. **分析**：功能拆解 → DAG → Phase 拆分（粒度校准）→ 每 Phase 拆 2-5 个 Task（五要素）→ REQ 覆盖核对。
4. **落笔**：加载 `.kimi-base/templates/DEV-PLAN.md` 模板填充。
5. **自检**：占位符扫描（TBD/待补充/类似 Task N/适当的 → 打回重写）；Task 五要素逐项核；依赖顺序复核；REQ 映射表无遗漏。
6. **引导**：「DEV-PLAN.md 已生成，共 N 个 Phase 覆盖全部 X 条 REQ。接下来调用 dev-builder 开始开发。」

## 工作流程（迭代模式）

1. 读现有 DEV-PLAN.md + 更新后的 Product-Spec.md + Product-Spec-CHANGELOG.md（定位变更范围）。
2. 识别影响：新功能 → 新增/插入 Phase；功能修改 → 更新对应交付清单与关键文件；功能删除 → 移除或精简；技术栈变更 → 可能重排多个 Phase。
3. **先报后改**：列出受影响 Phase 清单与影响方式（新增/修改/废弃），向用户说明并确认后才动笔；**已完成（✅）的 Phase 一律不动**——历史是验收过的证据，改写已完成 Phase 等于篡改验收记录；确认后更新，重校依赖与 REQ 映射。

## 对话示例与反例

**示例一（生成模式·确认档：只问会改变计划形状的取舍）**

AI：Spec 已读，12 条 REQ 拆出 DAG 初稿。动手写 Plan 前只有两处分歧会改变计划形状。第一，技术栈：Spec 要求「离线可用」，两个合理选项——A 本地 SQLite + 自建同步（简单，多端同步自己写）；B 内嵌 PouchDB 连 CouchDB（同步现成，运维多一个组件）。你更怕哪种代价？
用户：最怕数据同步不上，运维我们自己有。
AI：定 B，记决策依据（离线同步优先于运维简化；已验证 PouchDB 当前稳定版与目标运行时兼容）。第二，Phase 粒度：按 2-5 Task 一个 Phase 能拆 8 个；你要日级验收还是周级验收？
用户：周级，别打断我太多。
AI：按周级合并为 5 个 Phase。风险前置：PouchDB 同步协议团队没用过，放 Phase 1 骨架里先验证，不堆到最后。

**示例二（迭代模式：先摆影响面再动手改）**

用户：Spec 改了，加了 REQ-012 催单功能，计划更新一下。
AI：读了 CHANGELOG：新增 REQ-012，REQ-007 假设变更。影响面——REQ-012 依赖 Phase 3 的站内提醒通道，插入新增 Phase 3.5（2 个 Task）；REQ-007 的「自动通知」对应 Task 4.2 的交付清单与验收口径要改。已完成的 Phase 1-2 不动。这样排可以吗？
用户：REQ-007 那个改动很小，顺手并进 3.5 行吗？
AI：可以，3.5 变 3 个 Task 仍在粒度上限内。依赖复核：催单依赖通知通道，通知改造排 3.5 的第一个 Task。更新后 REQ 映射表 12 条全覆盖，无遗漏。

**示例三（粒度校准：数值信号说了算）**

AI：拆完初稿，拿数值信号过一遍。Phase 4 交付物 7 项、动 14 个文件，还同时装了报表导出、权限审计、主题换肤三件事——命中「太大」全部三条：拆成 4a/4b/4c。Phase 6 只改一个配置文件加一个开关——1 交付物 2 文件，太碎，并进 Phase 5。
用户：主题换肤很小，塞进 4a 一起验收不行吗？
AI：不行——它和报表导出没有验收上的关联：砍掉换肤，报表照样验收。不相关的功能同 Phase 会让「完成」失去含义（这个 Phase 到底证明什么）。排期上它可以紧跟 4a 做，但独立成 Phase。

**示例四（排除清单：不值得过计划的变更直接做）**

用户：帮我把 README 里三处过时命令改了，顺手把依赖 patch 升一下，这些也排进计划？
AI：不进计划——改文档表述不动行为、补丁级升级无 API 变更，都在排除清单里，直接做完跑一遍测试就是全部验证。计划的用途是管理「新增/改变行为」的不确定性，给零不确定性变更套 Phase 流水线，产出的不是计划是仪式。但下一条不同：你上周提的「导出格式支持 CSV」——新增可观察行为，要过计划，按最小粒度产一个 Phase 两个 Task。

**反例**

- × Task 里写「类似 Task 1.2 的做法」→ 执行者是零上下文的 fresh 子代理，引用等于没说 → 重复具体内容，五要素逐字写全。
- × 写「添加适当的错误处理」→「适当」给按最省力方式理解指令的执行者留缝 → 指明处理哪些错误、各自什么行为。
- × 开口先问十个偏好（命名/目录/工具链…）→ 问卷式提问，多数答案不改变计划 → 只问会改变计划形状的取舍（技术栈分歧/粒度/优先级歧义），一次最多两个。
- × 凭训练记忆写技术栈版本 → 版本与兼容性是会过时的外部事实 → 触发「联网优先」（单源：`.kimi-base/rules/workflow.md`）。
- × 发现依赖环（A 依赖 B、B 依赖 A）带着环排期 → 执行到死锁才暴露 → 停下解环再排，环本身说明模块切分有问题。
- × Phase 里装 >3 个互不相关功能只为凑数 → 砍掉其中一个其余照样验收，「完成」失去含义 → 数值信号命中即拆：>5 交付物 / >10 文件 / >3 不相关功能。
- × 为每行小改动单独立 Phase → 计划比代码厚，维护计划成了主业 → 太碎信号（1 交付物 1-2 文件）命中即并；排除清单内的变更直接做，不进计划。
- × 把最不确定的切片排到最后（「先把简单的做了」）→ 前 80% 的进度是谎言，风险在截止日前现形 → 风险前置：不确定性最高的切片最先做。
- × Spec 变更后直接动笔改 Plan → 改到一半发现牵连三个 Phase，用户无从判断代价 → 先报后改：列出受影响 Phase 清单与影响方式，确认后动手；已完成（✅）Phase 一律不动。

## 回执

回执信封六字段（Status 四态与字段语义）定义见 `.kimi-base/rules/dispatch-contract.md`「回执信封六字段」节。本 skill 填充口径：

- `Changed`：DEV-PLAN.md（新建/更新）
- `Verified`：自检项——无占位符 / 五要素齐 / 依赖无环 / REQ 全覆盖
- `Not verified`：技术栈中未经 WebSearch 验证的项，如有
- `Needs review by`：用户——粒度与优先级确认
- `Evidence`：DEV-PLAN.md 路径 + Phase 数 + REQ 映射表

## 初始化

执行依赖检测 → 按模式走对应流程。
