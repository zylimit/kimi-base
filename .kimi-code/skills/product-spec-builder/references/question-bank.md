# 问题库（question-bank）

## 定位与加载时机

这是追问纪律的约束工具，不是问卷脚本。默认走创造性追问；想接受敷衍时翻「不接受的答案」，想提前停时翻「接受标准」，不知问什么时翻「主问题」。

**加载时机**：探索档拉某条线时加载对应一节；五性面在覆盖检查器阶段加载；「AI 功能专项」仅当需求含 AI 功能时加载；「Agent 产品专项」仅当产品本身是 agent / 自主系统时加载。

线名与编号是内部工作语言，绝不对用户外露。

**条目五段结构**：覆盖意图（为什么问这维度）/ 主问题（默认抛的问题，计入主问题预算）/ 追问话术对（用户敷衍时的反击，"用户说 X → 你回 Y"）/ 接受标准（通过条件）/ 不接受的答案（必须驳回的样本）。

## 线一：as-is 真实故事

### 1.1 唯一用户与真实问题

- **覆盖意图**：锁定一个可指认的主用户和一件真实发生过的事，防"为所有人解决一切"。
- **主问题**：「这东西最先帮到哪一个人？他最近一次被这事卡住是什么时候，当时在干什么？」
- **追问话术对**：
  - 用户说"大家都能用" → 你回：「所有人等于没有人。第一版只伺候好一种人——是谁？明确先不做谁？」
  - 用户说"很多同事都抱怨" → 你回：「别人先放放。你自己上次被它坑是什么时候？那天从几点弄到几点？」
  - 用户给观点不给事 → 你回：「这是判断。给我一件真发生过的事——哪天、谁、卡在哪。」
- **接受标准**：一个可指认的人（岗位+场景）+ 一件带时间的真实事件 + 当天怎么收场的。
- **不接受的答案**："所有人 / 大家 / 用户们"；纯假设无实例；对你方案的赞美；描述的是功能不是处境。

### 1.2 现状流程与代价

- **覆盖意图**：用过去行为验证问题真实存在，把痛折算成时间、钱、风险。
- **主问题**：「这件事今天是怎么干的？从头到尾带我走一遍——经过几个人、几张表、几个群？」
- **追问话术对**：
  - 用户说"一般我们……" → 你回：「不说一般。上次是哪次？那次谁动的手、用了什么、最后谁拍的板？」
  - 用户说"挺麻烦" → 你回：「麻烦是多少？上次花了几个钟头？一个月来几回？错过一次的代价是什么？」
  - 用户说"早该有人做了" → 你回：「那你们为它花过钱吗——买过软件、雇过人、拉过外包？没有的话，是什么拦住了？」
- **接受标准**：有过去真实行为 + 代价被量化（小时/次数/金额/一次事故）+ 已有的 workaround。
- **不接受的答案**：只有未来意愿没有过去行为；"很烦很慢"不带数字；把"愿意付费"当证据。

### 1.3 关键一次的全链路复盘

- **覆盖意图**：用一个完整实例暴露手工传递、重复录入、靠某个人记着的环节——核心价值候选都藏在这。
- **主问题**：「挑最近一次最折腾的，从那件事发生到彻底了结，每一步谁、用什么、交给了谁？」
- **追问话术对**：
  - 用户跳步"然后就处理了" → 你回：「中间呢？他怎么知道该找谁的？那句话是在哪个群里说的？」
  - 用户只讲顺利的那次 → 你回：「不顺的那次呢？卡在哪一环、谁去捅开的？」
- **接受标准**：一条无断点的链路（人/工具/交接点俱全）+ 至少一个卡点定位。
- **不接受的答案**：跳步的理想路径；只说"系统里走一下"但那个系统根本不存在。

## 线二：受益受损者

### 2.1 受益者与买单者

- **覆盖意图**：分清谁的日子变好、谁掏钱、谁拍板——三者常不是同一人，不一致时流程要各写一条。
- **主问题**：「这事做成了，第一个松口气的是谁？掏钱买单的又是谁？是同一个人吗？」
- **追问话术对**：
  - 用户说"领导很支持" → 你回：「支持体现在哪？他愿意为这事动谁的考核、批多少预算？」
  - 买单者≠使用者 → 你回：「用的那位不掏钱，他凭什么愿意改习惯？上回推新工具，大家真用了吗？」
- **接受标准**：受益者、买单者、使用者分别指认到角色；不一致时两条用户流程都写。
- **不接受的答案**："公司受益"这类集体名词；说不清谁掏钱。

### 2.2 受损者与隐性规则

- **覆盖意图**：变差的人是隐性规则的来源——"财务一定要看到原始单号"这种约束只有问到受损者才冒出来。
- **主问题**：「这事做成了，谁的活会变多、谁的权会变少、谁可能不高兴？」
- **追问话术对**：
  - 用户说"没人会反对" → 你回：「上回上系统时谁最抵触？那次他拦住了什么？」
  - 用户说"就是走个流程" → 你回：「流程里谁有一票否决？他较真起来看什么？」
- **接受标准**：至少指认一个潜在受损者 + 一条他可能坚持的约束（写进 Spec「规则与例外」节）。
- **不接受的答案**："没人受损"；把抵触当态度问题而不是约束来源。

### 2.3 取舍与优先级

- **覆盖意图**：没有取舍就没有优先级，逼出"只能保一个"的答案。
- **主问题**：「列出来的这些里，只能上线一个，保哪个？哪个砍了你最不心疼？」
- **追问话术对**：
  - 用户全标 P0 → 你回：「全 P0 等于没优先级。上线前一天只够跑一个功能，留哪个？其余降 P1。」
  - 用户说"都要，都很重要" → 你回：「都重要等于没排序。客户明天验收只看一样，你给他看哪样？」
- **接受标准**：每个范围项有 P0/P1；P0 是发布最小集；能说出至少一条"这版明确不做"。
- **不接受的答案**：全 P0；没有不做清单；"都要做，先做简单的"。

## 线三：规则与例外

### 3.1 每条规则要一个例子和一个例外

- **覆盖意图**：例外比规则更暴露真实逻辑。
- **主问题**：「这条规矩，有没有哪次没照办？那次为什么？」
- **追问话术对**：
  - 用户说"没有例外" → 你回：「上个月最急的那单也走了全流程吗？谁给开的绿灯？」
  - 例外超过 3 个 → 你回：「这不像一条规则，像一类流程。哪几种情形值得各立一条规矩？其余砍掉。」
- **接受标准**：每条核心规则带一个实例 + 至少一个例外（或"确实无例外"的证据）。
- **不接受的答案**：只有规则文本没有实例；"一般没有例外"。

### 3.2 可建必可删

- **覆盖意图**：能创建的资源必须有删除/撤销/作废路径——默认追问项兼验收项，防只管生不管死。
- **主问题**：「这个（工单/账号/配置/单号）建错了怎么办——谁能删、删了留什么痕迹、删不掉时怎么作废？」
- **追问话术对**：
  - 用户说"不会建错" → 你回：「上个月手滑建错的那条后来怎么处理的？留在系统里碍事吗？」
  - 用户说"要删就删呗" → 你回：「删了之后它关联的记录怎么办——一起删、留痕、还是禁止删？谁有权删？」
- **接受标准**：每类可创建资源有明确消亡路径（删除/作废/归档）+ 权限 + 关联数据处理；写进验收条件。
- **不接受的答案**：只定义创建不定义消亡；"到时候再说"。

### 3.3 workaround 与绕过路径

- **覆盖意图**：workaround 即隐性知识——流程之外大家实际怎么绕，才是系统真正的需求边界。
- **主问题**：「规矩之外，大家实际是怎么绕的？哪条捷径人人都知道、但没人写进制度？」
- **追问话术对**：
  - 用户说"都按制度来" → 你回：「制度要求先审批后执行，上回半夜出事那次也先等审批吗？」
- **接受标准**：至少挖出一条真实 workaround，并判定它该被扶正、堵死还是容忍。
- **不接受的答案**："没有人绕"；把 workaround 当违规批一顿而不问它为什么存在。

## 线四：决策历史

### 4.1 前次尝试与失败原因

- **覆盖意图**：以前试过什么、为什么没成——不在同一个坑里摔第二次。
- **主问题**：「这个方向以前试过没有？上次卡在哪——技术、人、还是钱？」
- **追问话术对**：
  - 用户说"那次是供应商不行" → 你回：「供应商不行具体是哪件事？换一家就不会撞上吗？」
  - 用户说"当时没人推" → 你回：「这次谁来推？他每天有多少时间真花在这事上？」
- **接受标准**：前次尝试的死因定位到具体事件；本次相对上次改变了什么说得出。
- **不接受的答案**："以前没试过"但竞品/隔壁部门明明有；死因归因于"运气不好"。

### 4.2 既定约束与拍板人

- **覆盖意图**：分清"可讨论的"和"已定的"——已定的进决策依据标"既定，不接受讨论"，不浪费口舌。
- **主问题**：「哪些事是已经定了、我只能接受的？这事最后谁拍板，谁能一票否掉？」
- **追问话术对**：
  - 用户说"都可以谈" → 你回：「技术栈也能谈吗？数据放哪也能谈吗？上次有人谈成了哪件"不能谈"的事？」
- **接受标准**：既定约束清单（带"谁定的、当时为什么、现在还成立吗"）；拍板人与否决者指认到人。
- **不接受的答案**："没什么约束"；约束不问出处直接吞下且不记录。

### 4.3 时间与预算的硬边界

- **覆盖意图**：定变更轻重、裁范围都需要真实的时间和钱。
- **主问题**：「这版最晚什么时候必须能用？误了会怎样？预算和人手的天花板在哪？」
- **追问话术对**：
  - 用户说"越快越好" → 你回：「为什么是这个时点？有什么会、什么审计、还是客户合同卡着？误期的代价是什么？」
- **接受标准**：一个真实截止点（带来源）+ 误期代价 + 资源天花板。
- **不接受的答案**："越快越好"没有时点；预算"应该够"。

## 五性面

### 5.1 性能与容量

- **覆盖意图**：把"快"换成数字（韧性/性能档）。
- **主问题**：「多快算能用？哪个操作最不能慢——多少人同时用、数据量多大时？」
- **追问话术对**：
  - 用户说"要快" → 你回：「多快？查询两秒内出结果？高峰是早上九点全公司一起打开吗，多少人？」
  - 用户说"数据不多" → 你回：「三年之后呢？单子一个月几百还是几万条？」
- **接受标准**：关键操作有响应时间数字 + 并发/数据量量级 + 增长预期。
- **不接受的答案**："快、流畅"无数字；容量"应该不大"。

### 5.2 安全与权限边界

- **覆盖意图**：谁看得见谁、谁动得了什么；问不出指标也要问出"哪些模块碰不得"（安全档永不豁免）。
- **主问题**：「谁能看见什么？有没有哪种人绝对不能看某类数据——哪怕是管理员？」
- **追问话术对**：
  - 用户说"都要权限控制" → 你回：「具体到事：实习生能看工资吗？部门经理能改别部门的单吗？举一条"看得见但改不了"的。」
  - 用户说"内网，没事" → 你回：「上回数据泄露是哪次？从那以后立的规矩是什么？」
- **接受标准**：角色×资源×操作的边界至少覆盖核心数据；"碰不得"清单明确。
- **不接受的答案**："做好安全"一句话；权限全"管理员说了算"。

### 5.3 隐私与个人数据

- **覆盖意图**：识别哪些是个人信息、合规红线在哪（隐私档永不豁免）。
- **主问题**：「系统里存哪些能定位到具体人的数据——身份证号、手机号、位置、聊天内容？哪些按规矩不能出哪道门？」
- **追问话术对**：
  - 用户说"没什么敏感数据" → 你回：「员工的打卡记录算吗？客户的联系电话算吗？导出 Excel 发邮件算不算出门？」
- **接受标准**：个人数据清单 + 存储位置 + 外传边界 + 留存期限（答不出标 `[未知]`，确认途径写法务/合规）。
- **不接受的答案**："不敏感"但不列数据清单；合规问题无确认途径。

### 5.4 可靠性与故障容忍

- **覆盖意图**：问出"挂了会怎样"——哪些故障丢钱、哪些丢人、哪些无所谓（可靠性档）。
- **主问题**：「系统挂一小时会怎样？哪个功能挂了是天大的事，哪个挂一天没人发现？」
- **追问话术对**：
  - 用户说"不能挂" → 你回：「上回断网那次，现场是用纸和笔顶的吗？顶了多久？这次系统也要能那样顶吗？」
- **接受标准**：故障后果分级（丢钱/丢人/可缓）+ 数据能不能丢、丢多少的明确说法。
- **不接受的答案**："都要稳定"；数据丢失无说法。

### 5.5 韧性与五态强制

- **覆盖意图**：每个核心界面的加载、空、错误、成功、无权限五态显式问出来。一次一态——禁问"边界都处理了吗"这种永答"处理了"的 yes/no 问法（功能安全/韧性档）。
- **主问题**（逐态单独问，一轮一态）：
  - 加载：「数据加载那几秒，屏幕上是骨架、转圈还是干等？几秒算超时，超时显示什么？」
  - 空：「新用户第一次打开、一条数据都没有时看到什么？引导他干的第一件事是什么？」
  - 错误：「提交失败——断网、校验不过、服务器崩——分别显示什么文案？他下一步能重试、改、还是放弃？」
  - 成功：「操作成功了他怎么知道？页面变什么、要不要通知别人？」
  - 无权限：「没权限的人点进来，看到"无权限"还是干脆看不见入口？登录过期的呢？」
- **追问话术对**：
  - 用户说"正常显示就行" → 你回：「空结果和报错不能长一个样。这俩分别什么样，差在哪？」
  - 用户把多个行为捆一起"它校验完保存然后发通知" → 你回：「这是三个行为，拆开。每个各自失败了怎么办？」
- **接受标准**：核心界面五态各有明确行为；空态≠错误态；复合行为已拆成可独立成败的原子。
- **不接受的答案**："边界都处理了"；"正常显示"；被动语态"通知会被发出"（藏住谁发的）。

## AI 功能专项（仅当需求含 AI 功能时加载）

### 6.1 质量条：好样本与丢脸样本

- **覆盖意图**：AI 是概率性的，质量不钉死开发就在赌。
- **主问题**：「给我 5 个"答得好"的例子和 5 个"答得丢脸"的例子。最重要的那个质量维度，命中率到多少你敢上线——80% 还是 95%？掉到多少要报警？」
- **追问话术对**：
  - 用户说"要准一点" → 你回：「准是多少？10 次里错 2 次你能接受吗？错的是哪一种最不能忍？」
- **接受标准**：好/丢脸样本各 ≥5 + 命中率阈值 + 报警线。
- **不接受的答案**："要准"无数字；给不出丢脸样本（说明没见过真实的坏）。

### 6.2 触发方式：建议优先建信任

- **覆盖意图**：默认"建议/草稿由人确认"，自动执行要挣到信任才放开。
- **主问题**：「它是给建议、人来点头，还是自己直接干？错了谁兜底？」
- **追问话术对**：
  - 用户说"全自动" → 你回：「上线第一个月就全自动？错一单客户就跑了的那种也自动？先建议模式跑一个月看命中率行不行？」
- **接受标准**：每个 AI 功能明确建议/自动 + 从建议升级到自动的条件。
- **不接受的答案**：不分场景一律自动；说不出谁兜底。

### 6.3 失败兜底：绝不能做清单

- **覆盖意图**：最贵的错和"哪怕用户要求也绝不做"的清单，先于功能定下来。
- **主问题**：「这功能能犯的最贵的错是什么？它绝不能做什么，哪怕用户要求？AI 拿不准时，是说"我不确定"、给出处、追问、还是转人工？服务挂了或慢了，禁用提示、降级缓存、还是排队？」
- **追问话术对**：
  - 用户说"不会出什么大错" → 你回：「它给客户报错一个价、删错一条记录，算不算大错？」
- **接受标准**：绝不能做清单 + 不确定时行为 + 服务挂/慢时的降级策略。
- **不接受的答案**：跳过兜底；"出错了再说"。

### 6.4 延迟与成本

- **覆盖意图**：延迟和单价是产品级约束，不是实现细节。
- **主问题**：「必须多快——3 到 5 秒能接受还是要瞬时？流式输出行不行？一天大概跑多少次，单次成本有没有上限？」
- **追问话术对**：
  - 用户没想过成本 → 你回：「一次调用几分还是几毛？乘一天的调用量，一个月多少钱？谁批这笔预算？」
- **接受标准**：延迟上限 + 流式与否 + 调用量估算 + 单次/月度成本上限。
- **不接受的答案**："要快"无数字；成本"应该不贵"。

## Agent 产品专项（仅当产品本身是 agent / 自主系统时加载）

用户给目标、系统自主执行的产品才触发本节；传统界面应用跳过。

### 7.1 自主性分级

- **覆盖意图**：自主边界是 agent 产品的第一决策。
- **主问题**：「agent 能自己做到哪一步？哪些动作必须停下等人点头——写文件、删数据、花钱、对外发消息？」
- **追问话术对**：
  - 用户说"全自动" → 你回：「不可逆的也自动？删库、对外发函、下单付款？哪一步出错最贵，那步就该设审批门。」
- **接受标准**：每类动作的自主级别（自动/确认/禁止）划清；危险不可逆操作有审批门。
- **不接受的答案**："全自动"不分动作类别；危险操作无确认。

### 7.2 工具与权限

- **覆盖意图**：agent 靠工具行动，工具集与权限边界就是它的能力边界。
- **主问题**：「它能调哪些工具——读文件、写文件、跑命令、联网、调 API？每个工具什么权限级别？要不要留扩展口让人加工具？」
- **追问话术对**：
  - 用户说"什么都能干" → 你回：「工具越多越危险。先给最小集：缺了哪三个工具，核心那件事就干不成？」
- **接受标准**：工具清单 + 逐工具权限级别 + 扩展机制有无。
- **不接受的答案**：工具无边界；权限不分级。

### 7.3 记忆与上下文

- **覆盖意图**：上下文管理决定 agent 能扛多大任务、记多久，是核心工程不是细节。
- **主问题**：「一个任务做到几十步，前面的决定它还记不记得？超了怎么办——压缩、分段、还是查外部存储？跨会话要不要记用户偏好，记多久、记在哪？」
- **追问话术对**：
  - 用户没想过上下文 → 你回：「任务一长上下文必爆。第 50 步时它怎么知道第 3 步为什么那么定？」
- **接受标准**：上下文上限策略 + 超限处理 + 跨会话记忆范围与留存期限。
- **不接受的答案**：不考虑上限；记忆无留存说法（会撞隐私面）。

### 7.4 评估与可观测

- **覆盖意图**：agent 是概率系统，没 eval 就是盲飞——最容易漏的命脉。
- **主问题**：「怎么判断它这次干得好不好？有没有能反复跑的评估集？线上每一步能不能追？质量悄悄变烂怎么发现？」
- **追问话术对**：
  - 用户没想过 eval → 你回：「agent 今天对明天可能错。没有评估集就是闭眼上线——你拿什么发现它退步了？」
- **接受标准**：评估方式（评估集/指标/回归）+ 每步可追 + 退化可发现。
- **不接受的答案**：只靠人偶尔看；无任何评估。

### 7.5 成本与熔断

- **覆盖意图**：agent 烧 token，成本失控是产品级事故。
- **主问题**：「单任务的 token/成本上限多少？超了熔断吗？要不要按任务分模型——难的用贵的、简单的用便宜的？」
- **追问话术对**：
  - 用户没想过成本 → 你回：「一个死循环 bug 一晚上能跑出五位数账单。单次上限多少？到顶是停还是降级？」
- **接受标准**：成本上限 + 防失控熔断 + 模型路由策略（或明确不分）。
- **不接受的答案**：无上限；不防失控。

### 7.6 卡死检测与会话恢复

- **覆盖意图**：agent 会卡、会循环、会失败；长任务要能中断、恢复、追溯。
- **主问题**：「它卡住、死循环、反复失败时，怎么发现、怎么停、怎么报告？失败时的半成品——回滚、保留还是接着来？任务中断了能恢复吗，历史记录给谁看？」
- **追问话术对**：
  - 用户说"它自己会解决" → 你回：「它会反复试同一个错招。错几次该停？停了那半截活算谁的？什么时候必须交回给人？」
- **接受标准**：卡死/循环检测 + 失败兜底 + 交回人的条件 + 会话持久化与恢复。
- **不接受的答案**：假设它永远能自救；长任务不能中断恢复；无历史。
